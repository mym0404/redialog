# Domain Contracts

## Domain Glossary

- **Dialog**: an overlay controlled through imperative `show` and `hide` methods. Its presentation can be centered or a bottom sheet.
- **Dialog handle**: the ref and controls supplied by `useDialog`; `DialogHandle` exposes them through a render function.
- **Dialog parameters**: data passed to a typed `show` call and exposed to a custom dialog through `useDialogProps`.
- **Backdrop**: the layer behind dialog content, optionally pressable to dismiss the dialog.
- **Portal**: content rendered into a host instead of at the caller's location.
- **Portal host**: a destination that owns rendered portal content in its surrounding native layout.
- **Host ID**: every mounted host's required identity. A caller-supplied `hostId` takes precedence over the stable ID generated by `useId()`.
- **Named host**: a mounted host explicitly targeted by `hostId`, independent of the caller's ancestor chain.

## Dialog Lifecycle

Showing a dialog makes its content available for rendering. Hiding starts dismissal; content remains mounted until hide completion, then unmounts. Parameterized dialogs retain their parameters during dismissal and clear them through the hide-end callback. Preserve that callback when composing dialog props.

Backdrop dismissal and Android hardware-back dismissal are independently configurable. Only the active accessible dialog consumes the Android back event when back-press dismissal is enabled.

## Portal Routing

- Without `hostId`, a `Portal` selects the nearest ancestor host and throws when none exists.
- Without an ID, a `Dialog` renders inline unless `portal` is enabled. Supplying `hostId` enables portal rendering by itself.
- Every host registers an ID, including hosts whose IDs are generated automatically. Host IDs must be unique among mounted hosts in the same library runtime. Duplicate registration throws; unmounting a host releases its ID.
- An explicitly named destination never falls back to an ancestor. Missing hosts render no content until the destination mounts. Removal and later remounting follow the same rule.
- Changing a host's ID updates its registration. Changing a portal's destination removes its content from the old host and mounts it in the new one; child-local state can reset. An ordinary rerender of the same host must preserve child state.
- An unmounted portal must not leave content behind, including when unmount happens before deferred mounting completes. Removing one portal must not remove another portal sharing its host.
- Hosts render within their own native layout. Portal routing alone does not create a native modal, move accessibility focus, or trap focus.

The public API documentation and portal tests are the authoritative executable counterparts of these contracts.

## Dialog Accessibility

Dialogs register while their rendered content is mounted, including dismissal. A dialog in a shallower destination host takes priority over nested-host dialogs. Among dialogs at the same host depth, the latest mounted dialog is active. Non-active dialogs remain mounted but are hidden from accessibility and pointer input.

Accessibility layers identify their destination with the required host ID, host depth, and host-local portal key. Isolation compares host IDs rather than host-method object references.

When a top-level host's dialog is active, all top-level hosts hide their normal children, including nested hosts and dialogs. Each host keeps portal content in a separate overlay; dialogs never move to another host for accessibility. A nested-host dialog hides its own host's children, without hiding ancestors or unrelated normal content. Generic portals do not initiate isolation. Host-external content and inline-dialog surroundings are outside the isolation boundary.

Initial focus waits for layout and the opening animation, then targets the supplied native ref or a labeled fallback heading. Closing the active dialog reactivates the remaining dialog. When the last dialog closes, focus restoration to its supplied return-focus ref is scheduled for the next frame and runs only if no dialog is active then. The library does not discover the opener automatically.
